# Slack export payload and decoding

Measured from the delivery manifest on 2026-09-10 (353 emojis, 82 animated).

| Export | Animated WebP bytes | Still WebP bytes | Gzipped, base64 payload bytes |
| --- | ---: | ---: | ---: |
| Baseline: all 128px | 8,315,662 | 1,379,444 | 12,836,952 |
| Comparison: animations 64px, stills 128px | 4,670,062 | 1,379,444 | 7,928,820 |

The 64px comparison saves 37.6% of downloaded image bytes and 38.2% of embedded payload bytes. Script code adds a few KB. These are actual existing assets, not a pixel-area estimate. As of 2026-09-11 the exporter chooses sizes dynamically and enforces an 8,000,000-byte cap on the finished script. A full-catalog export uses 128px stills and 64px animations; small selections can retain 256px stills and 128px animations. Precomputed per-image gzip estimates let the worker skip oversized candidate combinations before downloading them. The finished script is always measured, with smaller-size retries if necessary. Per-export caching avoids downloading the same asset twice. Estimates are regenerated by the delivery batch script without re-encoding images.

The compact script previously decoded its entire base64 payload with `Uint8Array.from(atob(...), callback)`. An isolated Chromium comparison at 2x CPU slowdown with a 9.6 MB decoded payload measured:

| Decoder | Elapsed | Largest frame gap |
| --- | ---: | ---: |
| Previous full-payload conversion | 2,043 ms | 2,048 ms |
| 64 KiB base64 chunks, yielding between chunks | 923 ms | 20 ms |

This isolates data conversion; it does not measure DevTools paste parsing, clipboard access, uploads, or end-to-end export time. The generated script now uses bounded chunks and yields. The app paints a clipboard-stage wait message before copying, and large-export instructions explain the possible DevTools paste pause.

The functional browser suite exercises the actual full-catalog generated script at 2x CPU slowdown and requires its maximum frame gap to remain below 500 ms. It runs on a blank page and stops at the Slack hostname guard after decoding; it never contacts Slack. The separate 3G/4G export suite continues to measure application responsiveness and network behavior. Its earlier failures have not been declared resolved by this decoder change.

## Adaptive export validation (2026-09-11)

The full catalog produces **7,935,527 bytes**: 271 stills at 128px and 82 animations at 64px. The 33 focused unit/component tests pass, including size fallbacks, underestimated metadata, oversized refusal, replacement overhead, and the ZIP generator. Fourteen functional browser cases passed; the four affected cases were repeated after adding size estimates, including running the shell generator from a ZIP downloaded by the built app.

| Half-speed CPU profile | Export time | Maximum input round trip | Longest main-thread task | p95 frame gap |
| --- | ---: | ---: | ---: | ---: |
| 4g-half-cpu | 19.38 s | 136 ms | 261 ms | 50.0 ms |
| 3g-half-cpu | 50.68 s | 338 ms | 507 ms | 50.0 ms |

Both final runs pass the 8 MB size, 1 second input, and export duration checks. Both miss the strict p95 frame-gap requirement of **less than 50 ms**. The 4G run passes the 500 ms freeze checks; the 3G run records a 507 ms main-thread task and a 516.7 ms frame gap, exceeding those limits. The performance suite is not fully green. Full measurements, assertions and tested commit are retained in `performance-latest.json`. Slack calls in functional tests are mocked; no real emoji uploads or deletions were performed.
